# FinPilot AI — Security, Safeguards & Regulatory Compliance Architecture

## 1. Core Security Principles

FinPilot AI adheres to financial industry security benchmarks:
1. **Zero Live Execution Boundary**: No live order execution pathways exist within the software codebase. All order routing is bound to an isolated paper trading simulator.
2. **Deterministic Validation**: Price bounds, order sizes, account balances, and risk percentages are validated deterministically before any order matching or plan generation.
3. **No Direct Model Math**: Generative AI models are strictly prohibited from generating raw mathematical figures without verification against analytical Python models.
4. **Defense in Depth**: Password salting via native `bcrypt`, stateless HMAC-SHA256 JWT tokens, role-based route guards, and immutable audit logs.

---

## 2. Authentication & Authorization Architecture

### 2.1. Native Bcrypt Password Hashing
To guarantee stability and eliminate legacy passlib compatibility friction, FinPilot AI utilizes native `bcrypt`:
- **Salt Generation**: Cryptographically secure 12-round salt (`bcrypt.gensalt(rounds=12)`).
- **Password Hashing**: `bcrypt.hashpw(password.encode('utf-8'), salt)`.
- **Constant-Time Verification**: `bcrypt.checkpw(password.encode('utf-8'), hashed_bytes)` prevents timing attacks.

### 2.2. JWT Token Mechanics
- **Standard**: RFC 7519 JSON Web Tokens signed with HMAC-SHA256 (`HS256`).
- **Token Claims**:
  - `sub`: User ID
  - `email`: User email address
  - `role`: Role string (`ADMIN`, `PRO_TRADER`, `TRADER`)
  - `exp`: Expiration timestamp (default 1440 minutes / 24 hours)
- **Token Verification**: Handled centrally in `app.core.security.decode_token()` and injected via FastAPI's `get_current_user` dependency.

### 2.3. Role-Based Access Control (RBAC)
FinPilot AI defines three privilege tiers:
1. `TRADER`: Default user role. Can access dashboard, search instruments, formulate trade plans, execute simulated paper orders, view portfolio analytics, and chat with AI copilot.
2. `PRO_TRADER`: Elevated tier. Access to high-frequency paper simulations, advanced risk simulations (Monte Carlo), and extended historical candle downloads.
3. `ADMIN`: System superuser. Access to system health telemetry, user account suspension/reactivation, AI token billing logs, and compliance audit trail inspection.

## 3. Financial Paper Execution Guardrails

To prevent unintended financial loss or invalid simulation states, all paper trading requests pass through strict pre-trade validation checks (`order_validation.py`):
1. **Positive Numerical Inputs**: Quantity $\ge 1$, Limit Price $> 0$.
2. **Directional Coherence**: BUY requires sufficient available paper cash including estimated commission and 0.05% slippage; SELL requires sufficient open position units (short sales are rejected in cash accounts).
3. **Price Tick Sanity**: Rejects limit orders deviating by more than 20% from the current market price to prevent unrealistic fills.
4. **Market Status & Freshness**: Orders flag whether execution was during standard market hours or simulated queueing.

## 4. AI Copilot Safety Guardrails & RAG Grounding

### 4.1. Response Validation Pipeline
Every response generated by the AI copilot passes through `app.ai.response_validator.validate_and_sanitize()`:
- **Redaction of Guarantee Language**: Expressions such as *"guaranteed return"*, *"risk-free investment"*, *"100% win rate"*, or *"sure profit"* are strictly detected and redacted.
- **Mandatory Safe Harbor Injection**: All financial analytical responses automatically append statutory educational disclaimers.
- **Source Citation Enforcement**: RAG responses must link to verified filings or historical candle intervals.

### 4.2. Token Abuse & Rate Limiting
- Token usage is tracked per user in `ai_usages` table.
- System monitors prompt tokens, completion tokens, and calculated cost ($ USD) to prevent Denial of Wallet attacks.

---

## 5. Simulated Broker Gateway & Consent Logs

FinPilot AI provides mock broker adapters for Zerodha Kite Connect, Angel One SmartAPI, and Alpaca Markets:
- **Zero Real Credential Storage**: Only simulated client IDs and mock session tokens are stored. Real broker API secrets are rejected.
- **Explicit Consent Ledger**: Before any simulated trade is routed through a mock broker adapter, the user must explicitly submit consent, which is permanently recorded in `broker_consent_logs` with UTC timestamp and IP address.

---

## 6. Audit Trail & Observability

All security-sensitive operations trigger an audit record in the `audit_logs` table:
- Account authentication and failed password attempts
- User profile updates and risk tolerance adjustments
- Trade plan formulation and execution
- Simulated broker authorization events
- Administrative account status changes
